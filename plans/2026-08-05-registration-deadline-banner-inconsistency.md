# 首頁報名截止 banner 與後端實際開放不一致（誤報「已截止」）

> 輕量 plan（動手前的 spec）：目標 / 範圍 / 決策 / 驗收 / 工時。做完可丟；穩定規則再收進 `docs/`。

## 背景

2026/8/5 對正式環境（Lightsail k3s）跑完整核心流程測試時發現：首頁顯示「報名截止（星期一 23:59:59）**已截止**」，但實際用 UI 報名（週期 2026/8/11 ~ 8/18）後端回 `POST /api/register 200`、成功建立報名並觸發自動排團。前後端對「報名是否截止」的判斷不一致。

**關鍵領域規則**：王每週**星期二重製**（重製日 = Period.StartDate 的星期幾）。一個 raid 週是「週二 → 下週一」，報名截止設在該週期開打前的那個星期一（`DeadlineDayOfWeek=1`，實查 prod SystemConfig 得 `1 / 23:59:59`）。例如：
- raid 週 A：週二 08-04 → 週一 08-10，報名截止 = 前一個週一 **08-03**
- raid 週 B：週二 08-11 → 週一 08-17，報名截止 = 前一個週一 **08-10**
- 今天週三 08-05：週 A 已開打（週二 08-04 過了），玩家報的是**週 B**，截止 08-10 → 仍開著。

根因是兩邊用**不同的基準點**算截止時間：

- **後端（正確）**（`Domain/Entities/SystemConfig.cs` 的 `GetDeadlineForPeriod`，`RegisterService.cs` L158-161 用它擋）：相對**即將開打的 Period 起始日**（週二 08-11）回推截止 08-10 → 相對現在（08-04 UTC）在未來 → 放行報名。完全符合「週二重製、報到前一個週一」的規則。
- **首頁 banner（錯誤）**（`web/app/page.tsx` 的 `getThisWeekDeadline`, 約 L20-27）：**完全沒有「重製日」的概念**，天真地 snap 到「**當前日曆週的星期一**」——`config.deadlineDayOfWeek - now.getDay()`。週三 08-05 抓到的是 08-03（週 A 的截止，已過）→ `formatCountdown` 收到負數 → 顯示「已截止」。但玩家其實在報週 B，真正截止是**下**個週一 08-10。banner off by one week。

**影響範圍（比初版評估更廣）**：不是偶發「空窗期」。因為重製日在週二、截止在週一，**只要過了週二重製（週二～週日，一週 7 天佔 6 天），banner 都會抓到上一週的星期一、誤顯示「已截止」**；只有星期一當天剛好對上。等於一週有六天首頁都在誤報。

修正方向也因此更明確：**banner 不該用 `now` 的日曆週算，要改成像後端一樣「用即將開打的 Period 回推截止」**（單一事實來源，見下方範圍）。

## 嚴重度

**性質是 cosmetic / UX（非功能 break）**——banner 只是首頁顯示文字，誤報「已截止」不擋實際報名（硬去 `/register` 仍報得成、後端照收）。但**普遍性高**：一週 6 天（週二重製後到下個週一前）首頁都在誤報「已截止」，勸退效果不小（多數使用者看到已截止就不去點了）。綜合：**功能上低風險，但 UX 上不算邊角案例，值得修**。

## 為什麼 E2E 沒抓到

1. **E2E 完全沒對首頁 banner 做斷言**。`register.spec` 直接 `goto /register` 報名，從不經過首頁、也不檢查「已截止」文字 → banner 顯示對不對沒有任何測試在看。「不擋流程的顯示不一致」對 flow-based E2E 天生隱形。
2. **E2E 環境其實正好重現了 bug 條件卻沒斷言**：`db/seed-e2e.sql:40` 刻意把 Period 設成 `CURRENT_DATE + 10`（未來十天，讓後端截止落在未來、報名開著），這使 Period 與「今天」跨了日曆週 → banner 大概率也在顯示「已截止」。bug 就在眼前，但沒有斷言去抓。

→ 修這個 bug 時，**順手補一條 E2E 斷言**：首頁 banner 的截止狀態應與後端 `GetDeadlineForPeriod` 對同一週期的判斷一致（報名開著時 banner 不該顯示「已截止」），才能防止這類回歸再次溜過。

## 目標

讓首頁 banner 的「報名截止時間 / 是否已截止」與後端 `GetDeadlineForPeriod` 的判斷**一致**——banner 應該反映**目前開放報名的那個週期**的截止時間，而不是當前日曆週回推的時間，避免使用者被誤導以為不能報名。

## 範圍

- `web/app/page.tsx`：`getThisWeekDeadline` 改成「拿目前 latest Period 的 StartDate，套用後端同一套 `GetDeadlineForPeriod` 邏輯」算截止。
  - 前端要能取得 latest Period 的 StartDate。確認 `/api/period` 或現有端點有沒有回這個值；沒有的話評估補一個唯讀端點，或後端直接提供「本週期截止時間」讓前端不必自己重算（比較不會再漂移）。
- 決策傾向：**後端算好截止時間、前端只顯示**（單一事實來源），比前端重寫一份 deadline 計算好——避免以後兩邊公式再度分岔（這次的 bug 本質就是同一個邏輯前後端各寫一份）。

### 非範圍

- 不改後端的截止判斷邏輯（`GetDeadlineForPeriod` 是對的，以它為準）。
- 不動自動排團、報名本身的流程。

## 附帶發現（順手記錄，不一定這個 plan 處理）

- `Domain/Entities/Character.cs` 的 `Job` 欄位標 `[MaxLength(5)]`，但 `constants/jobs.ts` 有 6 字職業名（火毒大魔導士、冰雷大魔導士），且 DB 欄位是 `text`（無長度限制）、Dapper 不驗證 DataAnnotation → 這個標註**完全沒作用**，6 字職業實測能正常存取。屬誤導性殘留標註，建議移除或改成正確長度，但無功能影響、優先級低。

## 驗收

- [ ] 在「上一週截止已過、下一個開放週期報名仍開著」的時間點，首頁 banner 顯示的是**該開放週期**的截止時間與正確倒數（非「已截止」）
- [ ] banner 顯示的截止時間與後端 `GetDeadlineForPeriod` 對同一週期算出的值一致
- [ ] 真的超過開放週期截止時間後，banner 才顯示「已截止」，且此時後端也確實擋下報名（兩邊同步）
