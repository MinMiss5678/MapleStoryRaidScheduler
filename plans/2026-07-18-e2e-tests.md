# E2E 測試計畫：Playwright 打全端關鍵路徑

## Context

現有測試覆蓋兩層——unit（`Test/`，邏輯 + mock）、integration（`Test.Integration/`，持久層對真 Postgres）。**缺的是「整條路對使用者到底通不通」**：瀏覽器 → Next.js（`/api` proxy）→ .NET API → Postgres 全端一起走。

E2E 補的正是這塊，尤其**自動排隊金流路徑**（玩家報名 → `RegisterService.AutoAssignAsync` → `TeamSlotService` 媒合 → 前端看到隊伍）——這條跨前後端 + DB，unit/integration 各自都測不到「合起來對不對」。

**原則（重要，延續「不寫沒意義的測試」）**：E2E 慢、脆、貴 → **只測少數關鍵金流**，不求全。金字塔：unit 多、integration 中、**E2E 只挑錢在哪的路徑**。

## Approach

- **Playwright（TypeScript，放 `web/`）**：Next.js 官方推薦、跨瀏覽器、auto-wait 少 flaky。
- **打真全端**：用 docker compose 起 `database + backend + frontend`（bot 可略），E2E 對這個 stack 跑。獨立 `docker-compose.e2e.yml`（乾淨 DB + 固定 seed）避免污染 dev。
- **🔴 認證繞過（本計畫的核心難點）**：Discord OAuth 無法在自動化測試裡真登入。但認證是 **cookie-based**（`jwtToken` / `sessionId{discordId}` / `discordId`），所以**直接注入 cookie**：
  - **玩家**：預先簽一個 JWT（測試環境的 SecretKey）→ Playwright `storageState` / `context.addCookies` 種 `jwtToken` + `discordId`。
  - **管理員**：seed 一筆 `session` → 種 `sessionId{discordId}` + `discordId`。
  - **或**：後端加一個**只在 Testing 環境開**的 test-login 端點，直接發 cookie（較乾淨、不綁簽章細節，但多一個測試專用面必須鎖死非 prod）。
- **固定測試資料 + 重置**：seed 已知 boss/period/player/character（擴 `db/seed-demo.sql`）；spec 間 TRUNCATE 或重 seed 做隔離。

## Phase 1：Playwright scaffold（MVP 地基）

- `web/` 裝 `@playwright/test`、`playwright.config.ts`（`baseURL` 指 compose 的 frontend）。
- 一支 smoke test：首頁載入、標題正確。證明 harness 通。
- `webServer` 設定或前置腳本：確保 compose stack 起好才跑。

## Phase 2：認證接縫（繞過 Discord OAuth）★ 最關鍵 —— 定案：test-login 端點

- 後端加 `POST /api/test/login`（body: `discordId` / `discordName` / `role`）→ 直接發**跟 Discord 流程一樣的** cookie：玩家發 `jwtToken` + `discordId`；admin 則 seed 一筆 `session` + 發 `sessionId{discordId}` + `discordId`。全程不碰 Discord。
- **🔴 鎖死非 prod（不可省）**：只在 `ASPNETCORE_ENVIRONMENT != Production`（建議專用 `Testing`/`E2E` 環境）才 `MapPost` 這條路由——prod build 根本沒有這條路。保險再加一個共用 `secret header` 檢查。**這是認證後門，漏到 prod = 任何人可發 admin token。**
- Playwright fixture：spec 開跑前呼叫 `/api/test/login` 拿 cookie → 存進 `storageState` → 之後以登入態操作（玩家 / admin 兩種 storageState）。
- 驗證：以登入態載入受保護頁（`/character`）正確顯示、`layout.tsx` 讀到 role；admin 版能進 `/admin/*`。

## Phase 3：固定測試資料

- E2E 用 DB 的 seed：boss（含 `BossTemplateRequirement` 職業需求）、period（當期）、player + character。
- 重置策略：每個 spec 前重置到已知狀態（TRUNCATE + 重 seed，或每 spec 獨立資料）。

## Phase 4：第一條金流 E2E（跨全端）★

**玩家報名 → 自動排隊 → 看到隊伍**：
1. 以玩家身分（Phase 2 fixture）進 `/register`
2. 選角色 + 填可用時段 → 送出
3. 後端 `AutoAssignAsync` 媒合到暫定隊
4. 到 `/schedule`（或 `/scheduleResult`）→ **看到自己被排進某隊、職業/時段正確**

這條一次驗：前端表單 → proxy → API → 排隊演算法 → DB → 前端呈現。

## Phase 5：其餘關鍵流程（各一條）

- **補位**：published 隊有空缺 → 玩家填相符職業空槽 → 看到自己入隊（`IsManual`）。
- **管理員重排 + 發佈**：admin `/admin/schedule` 重排 → 保護隊保留、空位補滿 → 發佈 → 玩家端只看到 published。
- **可見性**：draft 隊玩家看不到、published 才看得到。

## Phase 6：CI（重、可能獨立/nightly）

- E2E 要**整個 stack**（frontend + backend + DB）→ 比整合測試更重。
- GitLab CI：用 `mcr.microsoft.com/playwright` 映像 + compose（或 services）起 stack；因為慢，**建議獨立 pipeline 或 nightly / 手動觸發**，不擋每個 MR。
- 失敗附 trace / screenshot / video（Playwright 內建）方便查。

## 進度

- ✅ Phase 1：Playwright scaffold——`web/playwright.config.ts`（baseURL 3000 + webServer 自動起 `next dev`）+ `e2e/smoke.spec.ts` + `e2e`/`e2e:ui` script；Vitest `exclude e2e/**`（免誤抓）；`.gitignore` 加 Playwright 產物。smoke（首頁未登入 Landing + 登入按鈕）**綠 11.4s**。

## 驗證

1. Playwright 本機對 compose stack 綠燈。
2. 金流 spec 真的走 前端→API→DB（非 mock），改壞排隊邏輯會讓它紅。
3. E2E 打 tag、與 unit/integration 分開跑，不拖慢日常快測試。
