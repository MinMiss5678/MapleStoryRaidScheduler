# E2E 測試計畫：Playwright 打全端關鍵路徑

## Context

現有測試覆蓋兩層——unit（`Test/`，邏輯 + mock）、integration（`Test.Integration/`，持久層對真 Postgres）。**缺的是「整條路對使用者到底通不通」**：瀏覽器 → Next.js（`/api` proxy）→ .NET API → Postgres 全端一起走。

E2E 補的正是這塊，尤其**自動排隊核心流程路徑**（玩家報名 → `RegisterService.AutoAssignAsync` → `TeamSlotService` 媒合 → 前端看到隊伍）——這條跨前後端 + DB，unit/integration 各自都測不到「合起來對不對」。

**原則（重要，延續「不寫沒意義的測試」）**：E2E 慢、脆、貴 → **只測少數關鍵核心流程**，不求全。金字塔：unit 多、integration 中、**E2E 只挑價值最高的關鍵路徑**。

## Approach

- **Playwright（TypeScript，放 `web/`）**：Next.js 官方推薦、跨瀏覽器、auto-wait 少 flaky。
- **打真全端**：專屬 `compose.e2e.yaml` 起 測試 DB + migrate + backend（Development）；前端 `next dev` 由 Playwright webServer 起、經 `BACKEND_API_URL` proxy 到 backend。（**不用**正式 `compose.yaml`——它是 prod 取向，見下方發現。）
- **🔴 認證繞過（核心難點，定案 = test-login 端點）**：Discord OAuth 無法自動化真登入；認證是 **cookie-based**（`jwtToken` / `sessionId{discordId}` / `discordId`）。→ 後端加 `POST /api/test/login`（鎖非 Production），依捏造身分發**跟正式流程一樣的** cookie，Playwright fixture 呼叫後即登入態。（放棄「預簽 JWT」——那要拿簽章金鑰 + 複製 token 結構。）
- **固定測試資料 + 重置**：seed 已知 boss/period/player/character（擴 `db/seed-demo.sql`）；spec 間 TRUNCATE 或重 seed 做隔離。（Phase 4 核心流程開始需要。）

## Phase 1：Playwright scaffold（MVP 地基）

- `web/` 裝 `@playwright/test`、`playwright.config.ts`（`baseURL` 指 compose 的 frontend）。
- 一支 smoke test：首頁載入、標題正確。證明 harness 通。
- `webServer` 設定或前置腳本：確保 compose stack 起好才跑。

## Phase 2：認證接縫（繞過 Discord OAuth）★ 最關鍵 —— 定案：test-login 端點

- 後端加 `POST /api/test/login`（body: `discordId` / `discordName` / `role`）→ 直接發**跟 Discord 流程一樣的** cookie：玩家發 `jwtToken` + `discordId`；admin 則 seed 一筆 `session` + 發 `sessionId{discordId}` + `discordId`。全程不碰 Discord。
- **🔴 鎖死非 prod（不可省）**：只在 `ASPNETCORE_ENVIRONMENT != Production`（建議專用 `Testing`/`E2E` 環境）才 `MapPost` 這條路由——prod build 根本沒有這條路。保險再加一個共用 `secret header` 檢查。**這是認證後門，漏到 prod = 任何人可發 admin token。**
- Playwright fixture：spec 開跑前呼叫 `/api/test/login` 拿 cookie → 存進 `storageState` → 之後以登入態操作（玩家 / admin 兩種 storageState）。
- 驗證：以登入態載入受保護頁（`/character`）正確顯示、`layout.tsx` 讀到 role；admin 版能進 `/admin/*`。

## Phase 3：E2E dev-mode stack（compose.e2e）✅ 完成

- `compose.e2e.yaml`：測試 DB（對外 5433）+ golang-migrate 套 migration + backend（`ASPNETCORE_ENVIRONMENT=Development` → test-login 才有效）。
- backend config 用 env 直帶：`ConnectionStrings__DefaultConnection`、`Jwt__SecretKey/Issuer/Audience`、dummy `Discord__*`；`build.context` = **方案根**（Dockerfile 從根 COPY 各專案）。
- 前端 `next dev`（Playwright webServer）經 `BACKEND_API_URL=http://localhost:5230` proxy 到 backend。
- **跑法**：`docker compose -f compose.e2e.yaml up -d` → **灌 seed**（backend 起完後：`docker compose -f compose.e2e.yaml exec -T e2e-db env PGPASSWORD=e2e psql -U postgres -d presentationdb < db/seed-e2e.sql`）→ `cd web && npm run e2e` → 收工 `docker compose -f compose.e2e.yaml down`。

## Phase 4：第一條核心流程 E2E（跨全端）★

**前置：固定測試資料** — seed boss（含 `BossTemplateRequirement` 職業需求）、period（當期）、player + character；spec 間 TRUNCATE + 重 seed 隔離。

**玩家報名 → 自動排隊 → 看到隊伍**：
1. 以玩家身分（Phase 2 fixture）進 `/register`
2. 選角色 + 填可用時段 → 送出
3. 後端 `AutoAssignAsync` 媒合到暫定隊
4. 到 `/schedule`（或 `/scheduleResult`）→ **看到自己被排進某隊、職業/時段正確**

這條一次驗：前端表單 → proxy → API → 排隊演算法 → DB → 前端呈現。

## Phase 5：其餘關鍵流程（各一條）

- **補位**：published 隊有空缺 → 玩家填相符職業空槽 → 看到自己入隊（`IsManual`）。
- **管理員重排 + 發佈**：admin `/admin/schedule` 重排 → 保護隊保留、空位補滿 → 發佈 → 玩家端只看到 published。
- **可見性**：draft 隊玩家看不到、published 才看得到。

## Phase 6：CI（重、可能獨立/nightly）

- E2E 要**整個 stack**（frontend + backend + DB）→ 比整合測試更重。
- GitLab CI：用 `mcr.microsoft.com/playwright` 映像 + compose（或 services）起 stack；因為慢，**建議獨立 pipeline 或 nightly / 手動觸發**，不擋每個 MR。
- 失敗附 trace / screenshot / video（Playwright 內建）方便查。

## ⚠️ 發現：`GetByNowAsync()` = 「StartDate 最新的 period」，非「含今天的」

- `PeriodQuery.GetByNowAsync()` 回**最新建立**的 period（rolling-week 模型，WeeklyPeriodJob 每週四建下一個）。
- backend 開機時 `WeeklyPeriodJob` 會自動建一個**未來 period**，StartDate 比 seed 的當期新 → `GetByNowAsync` 挑到它 → `GetByDiscordId` 撈不到 seed 的隊（在舊 period）→ 回空。
- **解（測試面）**：`db/seed-e2e.sql` **TRUNCATE 掉所有交易資料**，只建**一個**當期 period，確保它就是「最新」→ 回它。（curl 直打 API 佐證：刪掉 stray period 後 `GetByDiscordId` 立刻有回傳。）
- **✅ 已改名（清晰面）**：查詢層 `IPeriodQuery.GetByNowAsync` → **`GetActivePeriodAsync`**、`GetPeriodIdByNowAsync` → **`GetActivePeriodIdAsync`**（名實相符、行為不變）；服務層 `IPeriodService`/`PeriodController` 的 `GetByNow`（HTTP 路由 `[HttpGet("GetByNow")]` 契約）**保留不動**。全 241 單元測試綠。

## ⚠️ 發現：報名有截止時間，E2E 的 period 必須設「未來」

- `RegisterService.EnsureRegistrationOpen` 用 `SystemConfig.GetDeadlineForPeriod(period.StartDate)`——**截止日永遠在 period 開始前一週**（公式 `... % 7 - 7`）。
- seed 若把 period 設「今天」→ 截止日在**過去** → 報名被擋（500「目前已超過報名截止時間」）。
- **解**：`seed-e2e.sql` 把 period 設 **`CURRENT_DATE + 10 ~ +17`（未來一週）** → 截止日落未來 → 報名開著；隊伍時段也移進該未來 period。這其實才符合 app 真實模型（**當前 period = 即將開打的下週**）。E2E 才逼出這個時間相依的業務規則。

## ⚠️ 發現：現有 `compose.yaml` 是 production 取向，E2E 不能直接用

- 後端**沒設 `ASPNETCORE_ENVIRONMENT`** → 預設 **Production** → `TestAuthController` 回 404（我的環境鎖）。
- 前端是 **prod build**（`build: ./web`）→ `NODE_ENV=production` → 白名單 `test` 被排除 → proxy 403。
- → **E2E 需要專屬 dev-mode stack**：frontend `next dev`、backend `ASPNETCORE_ENVIRONMENT=Development` + 測試 DB + `BACKEND_API_URL`。**✅ 已用 `compose.e2e.yaml` 解決**（見 Phase 3）——Phase 2 隨之 live 驗證通過。
